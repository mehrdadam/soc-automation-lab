## معرفی پروژه

این پروژه، گردش‌کاری در Splunk SOAR را مستند می‌کند که فید RSS سایت [The DFIR Report](https://thedfirreport.com/) را بررسی می‌کند، گزارش‌های جدید را شناسایی می‌کند و از یک مدل هوش مصنوعی می‌خواهد برای هر گزارش، کوئری‌های پیشنهادی Splunk تولید کند. نتیجه در یک Custom List ذخیره می‌شود تا تحلیلگر بتواند آن را بررسی و پیگیری کند.

ایده اصلی، کوتاه‌تر کردن فاصله بین مطالعه یک گزارش تهدید و آماده‌کردن پیش‌نویس اولیه برای Detection Engineering است. خروجی مدل، پیشنهاد اولیه محسوب می‌شود؛ نه Detection Rule اعتبارسنجی‌شده و نه کوئری آماده استفاده در محیط عملیاتی.

**این مخزن مستندات پروژه را نگه می‌دارد و شامل سورس کد Python یا بسته قابل نصب Splunk SOAR نیست.** در اینجا معماری، تنظیمات، ساختار داده‌ها و نکته‌های فنی پیاده‌سازی ثبت شده‌اند.

## گردش‌کار چگونه اجرا می‌شود؟

```text
فید RSS سایت The DFIR Report
             │
             ▼
┌─────────────────────────┐
│ check_dfirreport        │
│ دریافت RSS و شناسایی    │
│ گزارش‌های جدید          │
└────────────┬────────────┘
             │ posts: [{url, title}, ...]
             ▼
┌─────────────────────────┐
│ demux_posts             │
│ جداسازی گزارش‌ها برای   │
│ پردازش مستقل هر گزارش   │
└────────────┬────────────┘
             ▼
┌─────────────────────────┐
│ build_prompt            │
│ ساخت بدنه درخواست مدل   │
└────────────┬────────────┘
             │ body
             ▼
┌─────────────────────────┐
│ HTTP app در SOAR        │
│ ارسال درخواست به 9router│
│ /v1/chat/completions    │
└────────────┬────────────┘
             │ parsed_response_body
             ▼
┌─────────────────────────┐
│ parse_ai_response      │
│ پردازش پاسخ و استخراج  │
│ کوئری‌های پیشنهادی      │
└────────────┬────────────┘
             │ splunk_queries
             ▼
┌─────────────────────────┐
│ update_seen_row         │
│ ثبت نتیجه در Custom List│
└─────────────────────────┘

parse_ai_response
        │
        ▼
   prompt block
   نمایش نتیجه برای تحلیلگر
```

در این جریان، `demux_posts` فهرست گزارش‌ها را به آیتم‌های جداگانه تبدیل می‌کند تا مراحل بعدی برای هر گزارش اجرا شوند. تابع `build_prompt` بدنه درخواست را می‌سازد و بلاک HTTP آن را به endpoint مدل ارسال می‌کند. سپس `parse_ai_response` پاسخ را پردازش می‌کند و `update_seen_row` اطلاعات گزارش و کوئری‌های پیشنهادی را در Custom List ثبت می‌کند.

بلاک `prompt` خروجی قالب‌بندی‌شده را برای بازبینی تحلیلگر نمایش می‌دهد. تابع `get_last_seen` نیز برای خواندن وضعیت فعلی لیست در ابتدای اجرا در نظر گرفته شده است.

## Custom Functionها

| تابع | وظیفه | ورودی‌ها | خروجی‌ها |
|---|---|---|---|
| `dfirreport_check_dfirreport` | دریافت RSS و برگرداندن گزارش‌های جدید | `limit` | `status`, `posts`, `new_count` |
| `dfirreport_demux_posts` | جداسازی گزارش‌ها؛ یک خروجی برای هر گزارش | `posts` | `*.url`, `*.title` |
| `dfirreport_build_prompt` | ساخت بدنه درخواست HTTP | `title`, `url` | `status`, `body` |
| `dfirreport_parse_ai_response` | پردازش پاسخ مدل و استخراج کوئری‌ها | `ai_response`, `title`, `url` | `status`, `title`, `url`, `splunk_queries`, `formatted_output` |
| `dfirreport_update_seen_row` | ثبت یا به‌روزرسانی اطلاعات یک URL | `url`, `title`, `splunk_queries` | `status`, `updated`, `count` |
| `dfirreport_get_last_seen` | خواندن وضعیت فعلی Custom List | — | `status`, `has_data`, `last_url`, `last_title`, `last_queries`, `count` |

نام‌ها مطابق نام‌گذاری استفاده‌شده در پیاده‌سازی هستند. کد این توابع در مخزن منتشر نشده است.

## ساختار Custom List

نام لیست:

`dfirreport_seen_posts`

| ستون | کاربرد |
|---|---|
| `url` | آدرس گزارش |
| `title` | عنوان گزارش |
| `splunk_queries` | کوئری‌های پیشنهادی تولیدشده برای گزارش |

ردیف اول لیست، header است و باید شامل `url`، `title` و `splunk_queries` باشد. این ردیف هنگام خواندن باید از پردازش داده‌ها کنار گذاشته شود و هنگام بازنویسی لیست حفظ شود.

`check_dfirreport` از URLهای ثبت‌شده برای تشخیص گزارش‌های قبلی استفاده می‌کند. پس از پردازش گزارش، `update_seen_row` اطلاعات مربوط به آن و کوئری‌های تولیدشده را ثبت یا به‌روزرسانی می‌کند. چند کوئری در ستون `splunk_queries` با یک خط خالی از هم جدا می‌شوند.

## راه‌اندازی و پیکربندی

این بخش تنظیمات لازم برای بازسازی گردش‌کار را توضیح می‌دهد. از آنجا که سورس کد توابع منتشر نشده است، این مستندات به‌تنهایی برای نصب یا اجرای مستقیم پروژه کافی نیستند.

### ۱. پیش‌نیازها

- Splunk SOAR با دسترسی لازم برای ساخت Custom Function و Playbook
- یک HTTP asset برای ارتباط با endpoint سازگار با OpenAI API
- دسترسی شبکه به endpoint مدل و API key معتبر
- دسترسی به فید RSS سایت The DFIR Report
- یک Custom List برای نگهداری گزارش‌ها و خروجی‌ها

در این پیاده‌سازی از [9router](https://github.com/decolua/9router) برای مسیریابی درخواست‌ها به مدل استفاده شده است.

### ۲. ساخت Custom List

در SOAR یک Custom List با نام `dfirreport_seen_posts` بساز و ستون‌های زیر را تعریف کن:

- `url`
- `title`
- `splunk_queries`

ردیف اول باید نام همین ستون‌ها را داشته باشد.

### ۳. پیکربندی Custom Functionها

توابع این گردش‌کار مسئول دریافت RSS، جداسازی گزارش‌ها، ساخت درخواست مدل، پردازش پاسخ و به‌روزرسانی Custom List هستند.

برای بازسازی پروژه، توابع را در SOAR ایجاد کن و پارامترهای ورودی و خروجی آن‌ها را مطابق جدول بالا تنظیم کن. سورس کد این توابع در این مخزن موجود نیست.

نکته‌های مربوط به پیاده‌سازی:

- نوع خروجی تعریف‌شده برای هر تابع باید با ساختار داده‌ای که برمی‌گرداند مطابقت داشته باشد. در این پیاده‌سازی از `item` و `list` استفاده شده است.
- توابع کمکی داخل بدنه تابع اصلی تعریف می‌شوند.
- برای نوشتن در Custom List، این پیاده‌سازی از REST endpoint با نام `decided_list` استفاده می‌کند؛ نه از `phantom.custom_list_add`.

### ۴. ساخت HTTP asset

یک HTTP asset ایجاد کن که به نمونه 9router دسترسی داشته باشد.

- **Base URL:** آدرس نمونه 9router، برای مثال `http://<host>:20128`
- **Headers:**
  - `Authorization: Bearer <api-key>`
  - `Content-Type: application/json`

بلاک HTTP در Playbook درخواست زیر را ارسال می‌کند:

`POST /v1/chat/completions`

بدنه درخواست از خروجی `body` تابع `build_prompt` گرفته می‌شود. آدرس و روش احراز هویت را با تنظیمات واقعی endpoint خودت تطبیق بده.

### ۵. اتصال بلاک‌های Playbook

بلاک‌ها را مطابق دیاگرام به یکدیگر متصل کن. دیتاپت‌های اصلی در پیاده‌سازی عبارت‌اند از:

- `build_prompt.title` ← `demux_posts:custom_function_result.data.*.title`
- `build_prompt.url` ← `demux_posts:custom_function_result.data.*.url`
- بدنه HTTP ← `build_prompt:custom_function_result.data.body`
- `parse_ai_response.ai_response` ← `post_data_N:action_result.data.*.parsed_response_body`
- ورودی‌های `parse_ai_response.title` و `parse_ai_response.url` ← خروجی‌های متناظر `demux_posts`
- `update_seen_row.splunk_queries` ← `parse_ai_response:custom_function_result.data.splunk_queries`
- ورودی بلاک Prompt ← `parse_ai_response:custom_function_result.data.formatted_output`

`post_data_N` باید با نام واقعی بلاک HTTP در Playbook جایگزین شود.

### ۶. زمان‌بندی

برای اجرای خودکار، یک Scheduler به Playbook اضافه کن. اجرای روزانه یکی از گزینه‌هاست؛ فاصله اجرا را متناسب با نیاز عملیاتی و محدودیت‌های محیط انتخاب کن.

## نکته‌های فنی و درس‌های آموخته‌شده

### ۱. اتصال بلاک‌ها به‌تنهایی باعث تکرار روی اعضای لیست نمی‌شود

اگر بلاک A یک لیست برگرداند و به بلاک‌های B و C متصل باشد، این اتصال به‌تنهایی تضمین نمی‌کند که B و C برای هر عضو لیست جداگانه اجرا شوند. الگوی demux با ایجاد خروجی مجزا برای هر عنصر، امکان پردازش one-to-many را فراهم می‌کند.

تابع `list_demux` در مخزن [phantomcyber/playbooks](https://github.com/phantomcyber/playbooks) نمونه‌ای برای بررسی این الگو است.

### ۲. دیتاپت‌ها ممکن است لیست برگردانند، نه مقدار تکی

دیتاپتی مانند `...data.*.url` ممکن است مقداری شبیه این تحویل دهد:

`['https://example.com/report']`

در حالی که تابع انتظار یک رشته مستقل را دارد:

`'https://example.com/report'`

اگر این تفاوت مدیریت نشود، مقدار لیست‌پیچیده ممکن است در Custom List ذخیره شود و مقایسه آن با URL اصلی نتیجه درستی ندهد. ورودی تابع را بررسی کن و در صورت نیاز، لیست تک‌عضوی را در مرز ورودی به مقدار تکی تبدیل کن.

### ۳. پاسخ مدل همیشه متن قابل استفاده ندارد

در استفاده از endpointهای روتری، ممکن است پاسخ شامل `tool_calls` باشد، در حالی که فیلد `content` خالی است. اگر مدل و endpoint از آن پشتیبانی می‌کنند، می‌توان `tool_choice: "none"` را در بدنه درخواست تنظیم کرد و در prompt نیز صریحاً از مدل خواست که از ابزار استفاده نکند.

فیلد `finish_reason` هم ارزش بررسی دارد. مقدار `length` نشان می‌دهد تولید پاسخ به محدودیت توکن رسیده است. مصرف بالای `reasoning_tokens` ممکن است در بعضی مدل‌ها در این وضعیت نقش داشته باشد، اما به‌تنهایی علت را مشخص نمی‌کند. محدودیت توکن و تنظیمات endpoint را متناسب با مدل بررسی کن.

### ۴. به‌روزرسانی Custom List در این پیاده‌سازی، کل لیست را جایگزین می‌کند

روش استفاده‌شده برای به‌روزرسانی لیست به این صورت است:

1. دریافت لیست با `GET decided_list/<name>`
2. تغییر آرایه `content` در حافظه
3. ارسال کل آبجکت با `POST`

هنگام بازنویسی باید header حفظ شود، ردیف‌های خالی مانند `['']` کنار گذاشته شوند و مقادیر لیست‌پیچیده پیش از ذخیره‌سازی نرمال شوند. این نرمال‌سازی می‌تواند ردیف‌هایی را که در اجراهای قبلی با مقدار نامناسب ثبت شده‌اند نیز اصلاح کند.

## امنیت و مدیریت خطا

- **ورودی غیرقابل‌اعتماد:** محتوای گزارش‌های خارجی را داده غیرقابل‌اعتماد در نظر بگیر. متن گزارش نباید بتواند دستورالعمل‌های موردنظر برای مدل را تغییر دهد یا باعث شود مدل از محدودیت‌های تعریف‌شده خارج شود.
- **اعتبارسنجی کوئری‌ها:** پیش از اجرا، صحت SPL، منطق تشخیص، محدوده جست‌وجو و سازگاری کوئری با داده‌های موجود را بررسی کن.
- **محافظت از کلید API:** کلیدهای API و اطلاعات احراز هویت را در کد، تصاویر، مستندات عمومی یا مخزن GitHub قرار نده.
- **محدودسازی دسترسی:** دسترسی به HTTP asset، endpoint مدل و Custom List باید متناسب با نیاز محدود شود.
- **خطاهای ارتباطی:** خطاهای HTTP، timeout، پاسخ ناقص، JSON نامعتبر و پاسخ بدون محتوای قابل استفاده باید جداگانه بررسی شوند. شکست درخواست نباید به‌عنوان تولید موفق کوئری ثبت شود.
- **کنترل کیفیت خروجی:** تولیدشدن کوئری به معنی صحیح‌بودن آن نیست. هر کوئری باید از نظر syntax، منطق تشخیص، پوشش داده و کارایی بررسی شود.
- **ثبت وضعیت پردازش:** وضعیت دریافت گزارش، پاسخ مدل و ثبت خروجی را بررسی کن تا مشخص باشد پردازش هر گزارش تا کدام مرحله پیش رفته است.
